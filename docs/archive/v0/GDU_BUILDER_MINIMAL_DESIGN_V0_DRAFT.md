# GDU Builder 最小实现设计 v0（草案）

状态：draft，尚未冻结，也不构成实现承诺。

## 1. 这份设计解决什么问题

简介：把前三轮 Pilot 中由人监督执行的流程，整理成一条以后可以写成程序的流水线。

专业表述：将 `BUILDER_PROTOCOL_V2.md` 的研究方法翻译为一个确定性的 Builder 编排状态机，并使其输出服从已经冻结的 GDU v0、Build Log v0 和 Validator v0 契约。

Builder 的职责是组织构建过程，不是证明 GDU 已经优于其他知识存储体系。是否更优仍需后续对照实验回答。

## 2. 本阶段明确不做什么

- 不接入任何模型 API，也不要求 API Key；
- 不决定使用 GPT、开源模型或具体参数；
- 不实现长文档分段、PageIndex、MinerU、OCR 或向量检索；
- 不实现 Reader，不构建数据库或界面；
- 不修改任何已冻结的设计、Schema、Validator 或 Build Log 基线；
- 不允许 Builder 读取 Gold、盲测答案、讨论记录或旧输出；
- 不把模型的隐藏思维过程作为 GDU 内容保存。

## 3. Builder 在系统中的位置

```text
权威 PDF + 已准备的抽取文本 + 固定配置
                    |
                    v
        确定性的 Builder 编排器
          |                   |
          v                   v
   来源读取接口          理解生成接口
   （暂不实现）          （暂不绑定模型）
          \                   /
           v                 v
        六个检查点 + 最多两次定向修正
                    |
                    v
       gdu.json + build_log.jsonl
                    |
                    v
             ARTIFACTS.sha256
```

核心原则：理解内容可以由模型提出，但运行规则不能由模型临时决定。

## 4. 最小组件边界

### 4.1 Orchestrator（编排器）

职责简介：流水线管理员。

它负责输入核验、阶段顺序、对象 ID、修正次数、日志顺序、Schema 验证、停止门、原子写入和哈希。它不负责凭空解释文章。

### 4.2 SourceReader（来源读取接口）

职责简介：按要求把原文的某些页交给理解模块。

v0 只定义接口，不规定内部采用整篇读取、分页、目录索引还是其他分段技术。PDF 是证据权威来源；抽取文本只能帮助定位，不能单独成为证据权威。

### 4.3 UnderstandingAdapter（理解生成接口）

职责简介：接收当前阶段允许看到的原文与公开工作状态，返回结构化的候选理解。

它可以在未来接模型，也可以先接人工夹具或固定测试数据。它不能直接写最终文件，不能改变阶段顺序，不能自行增加修正轮次，技术重试时也不能偷偷更换模型。

返回内容只包括候选对象、公开理由和证据位置，不要求或保存隐藏思维链。

### 4.4 ArtifactWriter / Validator（产物写入与验证）

职责简介：只把已经通过当前检查的内容写成合规文件，并在冻结前做最后验收。

写入器先完成临时文件，再整体替换目标文件，防止中途中断留下半个 JSON。Validator v0 作为最终契约检查器使用；Build Log 事件还须按其独立 Schema 逐行验证。

## 5. 运行输入契约

一次运行至少需要以下输入：

| 输入 | 用途 | v0 要求 |
|---|---|---|
| 原始 PDF | 唯一证据权威 | 必需，运行前核验 SHA-256 与页数 |
| 已抽取文本 | 导航和初步定位 | 必需，因为当前 GDU Schema 要记录其哈希和抽取系统 |
| `gdu.schema.json` | GDU 结构契约 | 必需，使用冻结版本 |
| `build_log.schema.json` | 单条日志事件契约 | 必需，使用冻结版本 |
| Builder Protocol | 构建方法 | 必需，记录名称、版本和哈希 |
| 固定运行配置 | 模型、推理等级、提示或配置哈希等 | 必需，运行开始后不得静默变化 |
| 输出目录 | 保存三项产物 | 必需，必须与输入和 Gold 隔离 |

固定运行配置还必须声明：单 Builder、禁止外部知识、最大定向修正次数为 2、最大技术重试次数为 1，以及预登记的模型标识和推理等级。若运行环境无法观测后两项，应诚实记录 `unavailable` 或 `not_observable`，不能猜测。

Gold、讨论日志、前次答案和待比较系统的输出不属于合法输入。

## 6. 运行状态

输入预检不计入六个理解检查点。最小状态如下：

```text
initialized
  -> input_verified
  -> checkpoint_1_complete
  -> checkpoint_2_complete
  -> checkpoint_3_complete
  -> checkpoint_4_complete
  -> checkpoint_5_complete
  -> verification_complete
       -> frozen_complete
       -> correction_required -> 回到受影响检查点
       -> provisional_complete（修正额度用尽）

任一阶段遇到真实技术故障：technical_retry -> 恢复原阶段
技术重试仍失败：technical_failed
输入不合法：input_rejected
```

状态只表示程序推进到哪里，不替代 GDU 对象本身的 `provisional` / `frozen` 状态。

## 7. 工作状态与正式产物

Builder 在运行中可以保留“公开工作状态”，包括候选对象、被否决或保留的有根据替代解释、证据定位、检查结果和待修正缺口。

工作状态有三条限制：

1. 不保存隐藏思维链；
2. 候选内容只有通过相应检查后才提升为 GDU 对象；
3. 崩溃恢复快照不是正式 GDU 包，不能冒充冻结产物。

## 8. 六个检查点

### CP1：来源与可观察物理结构

产出 `manifest`、`physical_structure` 和可供后续引用的来源定位骨架。核验 PDF 身份、页数、抽取文本身份、标题层级、表格、图、附录等可观察载体。

通过含义：知道“文章由哪些可定位的部分组成”，但尚未声称已经理解全文。

### CP2：语义单元与局部功能

产出 `semantic_units`，为每个单元标出边界、功能和来源范围。单元不必机械等同于章节；允许四层主干下出现按文章复杂度需要的小分支。

通过含义：每个主要部分在文章中“负责干什么”已有可检查的解释。

### CP3：原子断言、认识状态与证据

产出 `assertions` 和对应 `evidence`。每个断言必须足够原子化，区分作者主张、数据结果、方法设定、限制、解释和仍有根据的替代可能。

通过含义：关键说法能够回到 PDF 中的具体证据；没有把推测伪装成事实。

### CP4：关系

产出 `relations`，至少检查语义单元之间以及断言之间的支持、限定、依赖、对照、冲突或演化关系。

通过含义：GDU 不只是卡片堆，而能说明各部分为什么共同构成这篇文章。

### CP5：全局 GenerativePlan

产出五部分 `generative_plan`。它代表当前最能解释全文的主干理解，同时保留有证据的其他可能性。后续新证据可以通过新版本和追加日志改变旧主干，而不是假装旧判断从未存在。

通过含义：已经形成可以从全局重新组织文章的解释，但仍未自动获得冻结资格。

### CP6：双向核验与停止门

先做全局到局部、局部到全局的双向检查，并强制完成三项子检查：

- 跨载体冲突：正文、摘要、结论、表格和图之间是否不一致；
- 跨章节功能关系：不同部分在论证中如何协作；
- 限制与负向推断边界：文章没证明什么，哪些结论不能推出。

随后执行三联停止门：覆盖度、证据度、稳定度必须全部通过。只有三项全通过，才能写入 `freeze` 事件并把 GDU 状态设为 `frozen`。

每个检查点结束都写一条符合 Build Log v0 的 `checkpoint` 事件；真实的理解变更按需要写 `revision` 事件，而不是为凑日志机械记录。

## 9. 定向修正规则

若 CP6 未通过，必须生成公开、具体的缺口清单。每个缺口至少说明：失败维度、涉及对象、来源页或待查范围、失败原因和应回到的最早检查点。

修正只能回到受影响区域，不能重跑整篇来碰运气；不能查看 Gold；不能换模型；不能改变提示或配置。每轮修正后重新执行受影响检查和 CP6。

最多允许两轮定向修正：

- 第 0 次：主构建；
- 第 1、2 次：仅修正明确缺口；
- 第 2 次后仍未通过：结束为 `provisional_complete`，诚实保留未完成项。

研究上，这个上限用于防止 Builder 通过无限返工获得不可比较的优势。

## 10. 技术重试与语义修正必须分开

技术重试只处理读取失败、调用中断、输出传输损坏等非语义故障。最多一次，并且必须使用相同模型、相同参数、相同输入范围和相同阶段请求。

技术重试不消耗两次语义修正额度，但必须写 `technical` 事件。若重试仍失败，运行结束为 `technical_failed`，不能把技术失败包装为“文章无法理解”。

模型返回结构合法但内容质量不足，属于语义检查失败，不属于技术故障。

## 11. 输出契约

正式运行只产生三项核心产物：

1. `gdu.json`：当前结构化理解；
2. `build_log.jsonl`：追加式公开演化日志；
3. `ARTIFACTS.sha256`：前两项文件的字节完整性清单。

冻结结果：

- `gdu.json` 状态为 `frozen`；
- 停止门三项全部通过；
- `build_log.jsonl` 最后一条且唯一的冻结事件为 `freeze`；
- 三项文件满足 Validator v0 和 Build Log v0 契约。

修正额度用尽时，仍输出状态为 `provisional` 的三项文件，但不写 `freeze` 事件。`ARTIFACTS.sha256` 只表示文件未被悄悄改变，不表示理解已经完成或冻结。

输入拒绝或无法形成 Schema 合法快照的技术失败，不得伪造 `gdu.json`。具体的进程级错误报告格式留到实现设计，不加入 GDU 正式包。

## 12. 确定性控制与模型自由的分界

程序必须确定性控制：

- 输入哈希与隔离；
- 阶段顺序和允许回退点；
- ID 分配及引用闭包检查；
- 修正轮数和技术重试次数；
- Build Log 的逻辑时间与追加顺序；
- Schema 验证、停止门、文件写入和 SHA-256。

理解生成模块可以判断：

- 语义单元边界和局部功能；
- 哪些断言值得保留及其认识状态；
- 有证据的关系和替代解释；
- 当前最能解释全文的 GenerativePlan；
- 哪些内容仍不确定。

这个分界使未来的小模型、大模型、人工 Builder 或不同长文档读取方案可以在同一实验框架下公平比较。

## 13. 与冻结契约的一致性审计

| 冻结约束 | 本设计如何遵守 |
|---|---|
| 四层主干可随文章复杂度出现小分支 | CP1–CP5 生成固定主干块，语义单元内部允许必要分支 |
| 当前最佳解释必须保留有根据的其他可能 | CP3、CP5 保存认识状态和替代解释；变化写 revision |
| 后续理解可改变旧主干且历史不可抹除 | 新版本 GDU + 追加式 Build Log，不原位伪造历史 |
| 单一权威文档、证据可回指 | PDF 为唯一证据权威，文本仅导航 |
| 共同停止条件 | CP6 同时要求 coverage、evidence、stability |
| 最多两次定向修正 | 固化在编排状态机，不交给模型决定 |
| 只允许一次真实技术重试 | 单独计数并写 technical 事件 |
| 单 Builder、单次预登记主运行 | 配置固定，禁止候选赛马和静默换模 |
| frozen 包需要日志与哈希清单 | 冻结前调用 Validator，并让 freeze 指向外部清单 |
| 不改冻结 Validator | 作为现成检查器调用；若以后增强则新建版本 |

## 14. 已确认的 provisional 输出规则

未通过停止门且两次定向修正额度已用尽时，Builder 仍生成：

- 状态为 `provisional` 的 `gdu.json`；
- 不含 `freeze` 事件的 `build_log.jsonl`；
- 覆盖前两项文件的 `ARTIFACTS.sha256`。

哈希只回答文件是否发生变化，不回答理解是否合格；真正的冻结资格仍由 GDU 状态、三联停止门和最后的 `freeze` 事件共同表示。

该规则已确认。下一阶段可以定义接口字段和伪代码；在其确认前仍不实现 Builder。
