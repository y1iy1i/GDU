# GDU 盲 Builder 通用最小运行协议 v2（草案）

> 状态：讨论后草案，尚未冻结、不得用于正式运行  
> 版本：`gdu-builder-protocol-v2-draft`  
> 日期：2026-08-18  
> 来源：在冻结的 Pilot 01 Protocol v1 之上作最小方法修订  
> 目的：在不泄露 Gold 的条件下，对预注册来源执行一次 Schema 无关、跨论文可复用的盲构建。

## 1. 已确认：来源输入与权威性

### 允许输入

- `paper.pdf`：本次预注册的权威原文；具体 SHA-256 只写入本次 `INPUT_MANIFEST.sha256`。
- `paper.txt`：从同一原文生成的搜索与定位辅助；具体 SHA-256 只写入本次 `INPUT_MANIFEST.sha256`。

### 使用规则

- PDF 是唯一权威内容来源。
- `paper.txt` 只能用于关键词搜索、候选位置发现和快速导航，不能独立支撑正式判断。
- 提取文本可能丢失分栏、表格、公式、图注或阅读顺序；正式阅读顺序、表图数值、页码和证据必须回到 PDF 核验。
- 证据页码使用从 1 开始的 PDF 物理页码。
- PDF 与文本提取物发生冲突时，以 PDF 为准，并在构建记录中保留冲突。

### 禁止输入

- 本次来源对应的任何 Gold、Gold 哈希或评分规则；
- 方法讨论日志、当前对话及其中出现的来源解读；
- Gold 评分规则、Gold 派生摘要或任何论文特定提示；
- 外部论文摘要、解读、作者访谈或相关资料。

## 2. 已确认：通用构建规则的详细程度

Builder 获得完整的通用 GDU 构建方法，但不获得任何针对本次来源的答案、重点提醒或评价线索。目标是检验既定方法能否实例化到未知文档，而不是要求模型自行发明 GDU 方法。

### 四层通用流程

1. **物理与来源层**：确认来源身份、物理页、可观察标题和版面对象。
2. **局部语义层**：划分来源锚定的语义单元，生成原子判断并绑定证据。
3. **关系与全局计划层**：发现局部及跨章节关系，恢复目标、核心意义、内容选择、组织方式和约束。
4. **双向核验与冻结层**：用全局理解回查局部，用局部证据修正全局，保留重要替代解释和修订，再执行停止检查。

### 六个必经检查点

1. 来源与可观察物理结构；
2. 语义单元边界及局部功能；
3. 原子判断、认识论身份与直接／组合证据；
4. 单元—单元及判断—判断关系；
5. 五问式 GenerativePlan；
6. 全局—局部一致性、证据完整性、稳定性与停止状态。

### 通用认识论规则

- 区分作者明确／可蕴含内容与 Builder 的分析性解释。
- 先生成关系或计划候选，再回到 PDF 做定向核验。
- 不把“可能解释”升级为已证实因果，不把局部实验外推为普遍规律。
- 对有根据的竞争解释保留主要解释、替代解释及其证据差异。
- 后续全局理解可以修正早期主干，但关键修订必须进入构建记录。
- 只在覆盖、证据和稳定性联合条件满足时正式结束；否则输出暂定快照及未完成项。

### 防止论文特定答案泄漏

- 通用规则不得出现论文中的模型名、模板编号、语言对、具体实验结果或 Gold 判断。
- 不提供“重点检查某表格／某冲突／某结论”等针对本文的提示。
- 协议只描述所有文档都适用的理解动作和输出要求。

## 4. 已确认：交卷形式

本阶段输出为 Schema 无关的结构化 Markdown 文件 `BUILDER_OUTPUT.md`，不直接生成最终 `gdu.json`。

### 七个逻辑部分

1. 来源身份；
2. 可观察物理结构；
3. 语义单元；
4. 原子判断；
5. 关系；
6. 五问式 GenerativePlan；
7. 证据索引。

### 临时稳定编号

- `U-###`：语义单元；
- `A-###`：原子判断；
- `R-###`：关系；
- `E-###`：证据。

所有关系、计划判断、限制和解释都通过编号引用已经列出的对象，不靠模糊自然语言指代。编号只要求在本次冻结输出内稳定，不预先决定最终 Schema 的字段或嵌套方式。

### 最低表达要求

- 判断标明作者归因内容或 Builder 分析性解释，并标明内容、功能、计划或显著缺失类别。
- 关系只使用单元—单元或判断—判断两个端点层级。
- 证据使用 PDF 物理页码、所在章节／表图和简短定位信息；文本提取物不是独立证据。
- GenerativePlan 引用已经建立的判断和证据，不成为第二套事实来源。
- 有根据的竞争解释必须并列呈现，不强行合并为单一结论。

## 5. 已确认：轻量构建与修订记录

除 `BUILDER_OUTPUT.md` 外，Builder 单独生成 `BUILD_TRACE.md`，记录带顺序与时间标记的重要构建事件，不保存完整内部思维过程。

### 必须记录的事件

- 初始构建计划和计划发生的实质变化；
- 六个检查点的开始、完成或未完成状态；
- 触发定向重读的重要疑点或新证据；
- 会改变语义单元、主干判断、关系或 GenerativePlan 的修订；
- 高影响竞争解释的保留、淘汰或主次变化；
- 三项强制子检查的状态、范围、发现对象及未解决缺口；
- 最终停止门检查及尚未完成的事项。

### 三项子检查的轻量审计记录

每项子检查在 `BUILD_TRACE.md` 中只记录以下内容：

- 状态：`已检查并形成结果`、`已检查但不适用` 或 `尚未完成`；
- 实际检查的高影响对象或论证链范围；
- 若有实质发现，引用已经进入 `BUILDER_OUTPUT.md` 的对象编号；
- 若不适用，记录简短理由；
- 若尚未完成，记录缺口及其触发的定向重读。

检查过程不替代正式语义结果。影响理解的冲突、功能依赖和负面约束必须使用既有 `U-###`、`A-###`、`R-###`、`E-###` 或 GenerativePlan 表达并进入 `BUILDER_OUTPUT.md`。检查完成但没有实质发现时，不为满足格式制造空对象。

### 修订事件的最小字段

- 事件编号与 ISO 时间；
- 所属阶段；
- 触发原因；
- 修改前的对象引用与简短内容；
- 修改后的对象引用与简短内容；
- 支持修改的证据编号；
- 对其他对象的影响；
- 是否仍保留替代解释。

### 不记录的内容

- 逐 token 或逐句内部思维；
- 没有改变理解对象的措辞润色；
- 重复搜索、重复确认和无结果的常规操作；
- 无法由输出对象或来源证据核验的自我叙述。

轻量记录用于研究“后来的全局理解怎样改变早期局部主干”，而不是把冗长过程本身当作正确性的证据。

## 6. 已确认：检查轮次与停止门

### 三轮主流程

1. **局部自下而上构建**：完整阅读来源，建立物理结构、语义单元、初步判断和证据。
2. **全局自上而下构建**：发现跨章节关系，恢复 GenerativePlan，并用全局理解检查局部功能与判断。
3. **双向核验**：定向复核高影响结论、表图、限制、认识论身份、证据和全局—局部一致性，并完成下列三项强制子检查。

### 第三轮的三项强制子检查

“高影响”指足以改变核心研究问题、主要结论、关键比较、全局解释、适用范围或重要限制的内容，不等同于全文所有句子。

#### A. 跨表达载体冲突检查

- 对高影响判断，定位实际存在且相关的正文、表格、图、摘要和结论表述。
- 比较它们的数值、方向、适用范围和确定性强度，不因措辞相近就默认一致。
- 发现不一致时，同时保留双方来源位置和证据，不静默合并或省略冲突。
- 若依据来源权威性规则作出主次判断，仍须保留原冲突和判断依据。
- 次要判断只在出现具体疑点时定向核对，不执行全文句子的组合式穷举。

#### B. 跨章节功能关系检查

- 沿核心论证链检查重要章节或语义单元：它提供什么，后续哪个对象使用它，以及它如何支撑、操作化或限制后续判断。
- 优先恢复与核心研究问题相关的数据—方法—结果—限制等实际依赖，不只停留在“本节介绍什么”的局部标签。
- 使用已有语义单元、判断、关系和证据表达有根据的连接；无法建立来源支持的连接时不强行补齐。
- 不生成所有章节的两两关系矩阵。

#### C. 限制与负面推断边界检查

- 对高影响结论和关键限制检查：来源实际支持到哪里、容易被扩大成什么、什么范围或证据阻止这种扩大解释。
- 区分作者明确提出的边界与 Builder 根据研究范围、限制、反例或证据缺口形成的分析性边界，并分别标明认识论身份。
- 只有存在具体来源范围或证据依据时才持久化负面约束；不凭空发明风险，不设置最低数量，不为完成格式凑条目。
- 谨慎措辞不能替代明确边界；若一项过度推断会实质改变核心理解，应明确表达“现有证据不能推出什么”。

### 联合停止门

- **覆盖度**：重要章节、核心论证链和限制已经进入结果；三项强制子检查均为“已检查并形成结果”或“已检查但不适用”；未覆盖处明确列出。
- **证据度**：持久判断与关系均已完成证据检查；无法确定者明确标为不确定，不用推测补齐。
- **稳定度**：最近一次核验不再改变主干判断或 GenerativePlan；仍有变化则说明尚未稳定。

只有三项同时满足，才输出正式完成状态。

任一强制子检查为“尚未完成”时，覆盖度不得判定为通过。子检查发现实质冲突、关系缺口或负面推断缺口时，相关内容未进入正式对象并完成证据检查前，覆盖度或证据度不得判定为通过。

### 有界定向修正

- 停止门未通过时，最多执行两次由具体缺口触发的定向重读与修正。
- 每次只重读与缺口相关的页面，并在 `BUILD_TRACE.md` 记录触发原因、对象变化和证据。
- 两次后仍未通过时，输出暂定快照、未完成项和失败的停止条件，不继续无界循环，也不为满足格式强行生成结论。

循环上限按逻辑修正轮次计算，不按底层模型调用次数计算；模型调用与失败重试另行规定。

## 7. 已确认：上下文与文件系统隔离

盲 Builder 必须在独立干净工作区和不继承当前对话的全新任务中运行，仅靠提示词要求“不看 Gold”不构成充分隔离。

### 输入白名单

干净工作区在运行开始时只能包含：

- `paper.pdf`；
- `paper.txt`；
- 冻结后的通用 `BUILDER_PROTOCOL_V2.md`；
- 只列文件名、大小和哈希的输入清单。

### 明确禁止

- Gold、Gold 哈希、评分规则、讨论日志、当前或历史对话；
- 任何论文特定中文解读、提示、摘要或已有 Builder 输出；
- 外部网页、论文解读、作者材料及联网搜索；
- 从当前任务派生且继承上下文或共享答案文件的子 Agent 作为正式盲 Builder。

### 执行顺序

1. 创建独立干净目录并复制白名单文件；
2. 核对文件数、文件名、大小和 SHA-256，执行禁用文件名与内容提示扫描；
3. 新建不继承当前对话的任务，以干净目录作为唯一工作区；
4. Builder 只在该目录读取和写入；
5. 运行结束后先冻结 `BUILDER_OUTPUT.md`、`BUILD_TRACE.md` 和运行清单并计算哈希；
6. 冻结完成后，才将结果带回当前研究任务与 Gold 对照。

输入清单固定命名为 `INPUT_MANIFEST.sha256`，列出 `paper.pdf`、`paper.txt` 和 `BUILDER_PROTOCOL_V2.md` 的哈希。清单本身不包含论文内容或评价提示。

### 隔离声明

该设计防止显式 Gold 和讨论记录泄漏，但不能证明模型预训练中从未见过论文；潜在预训练记忆继续作为 Pilot 限制记录。

## 8. 已确认：单次预注册主运行与失败重试

每次正式实验只接受一次预注册的完整有效主运行，不因输出质量不理想而重新生成或挑选更好的结果。

### 运行前必须固定

- 模型标识与推理配置；
- Builder 协议版本与哈希；
- 输入白名单与各文件哈希；
- 三轮主流程、最多两次定向修正和输出要求；
- 技术失败判据与重试上限。

### 允许技术重试的情况

- 输入文件无法读取或损坏；
- 服务错误、任务意外中断或工具不可用；
- 输出文件未写入、损坏或无法校验；
- 有可观察证据表明协议没有完整执行。

### 禁止重试的情况

- 理解结果不够好；
- Gold 命中率可能较低；
- 主干判断、关系或 GenerativePlan 与研究者预期不同；
- 希望更换模型或提示以取得更漂亮的结果。

发生允许的技术失败时，最多重试一次；必须在运行清单中记录失败时间、可观察错误、已产生文件及处置。不得查看 Gold 后决定是否重试。正式多次重复与多模型比较推迟到方法跑通后的实验阶段。

### 冻结输出包

- `BUILDER_OUTPUT.md`：七部分结构化理解结果；
- `BUILD_TRACE.md`：轻量关键构建与修订事件；
- `RUN_MANIFEST.md`：实际模型、配置、时间、协议与输入哈希、停止状态和重试记录；
- `OUTPUTS.sha256`：前三个文件的 SHA-256 校验值。

`OUTPUTS.sha256` 生成后，前三个文件不得原位修改；发现错误时保留原输出并创建带新版本号的更正文件。

## 9. 已确认：模型配置与通用方法分离

- 通用协议不硬编码某个论文或某个模型；每次正式实验在接触 Gold 和运行前，单独预注册模型标识与推理档位。
- **运行方式**：单一 Builder、标准模式；不启用多 Agent，不把不同阶段分派给不同模型。
- **模型不可用**：停止并报告，不得静默切换到其他模型、档位或模式。
- **结果选择**：只接受第一次完整有效主运行，不生成多个候选再挑选。
- 做跨论文方法比较时，除非研究问题明确检验模型差异，否则优先保持模型和推理档位不变；任何变化都必须预先记录并作为比较限制。

运行清单必须记录请求模型、实际显示模型、推理档位、任务开始与结束时间、协议哈希、输入哈希、技术失败和重试情况。若应用无法显示精确模型快照，只记录可观察到的模型标识并把这一点列为复现限制，不猜测底层版本。

## 10. 当前边界

- 本协议不定义最终 Schema，不修改旧 Schema。
- 本协议规定 Builder 的理解与核验动作，不等同于 Python Builder 实现。
- v2 草案尚未冻结，不得用于正式盲运行。
- 为避免根据第二篇材料继续定制规则，应先完成本草案的通用性、泄漏和差异审查并冻结，再选择或打开下一篇验证来源。
