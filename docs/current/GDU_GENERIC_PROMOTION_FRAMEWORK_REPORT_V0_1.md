# GDU 通用生长晋升框架报告 V0.1

## 实验问题

前两次闭环分别处理了财务数字对账和论文方法来源冲突，但使用了两套独立的晋升函数。本实验检查：GDU 能否抽出稳定的生长骨架，只把真正的领域差异留给插件。

## 框架边界

通用层现在统一负责：

1. 候选必须保持隔离状态，不能跳过验证直接写图；
2. 文档标识、源文件哈希、证据定位和候选引用必须完整；
3. 新旧节点 ID 不能冲突；
4. 插件不能篡改原始图或候选输入；
5. 每个新证据和命题必须记录生长事件，证据还必须保留原文定位与源哈希；
6. 写入后的整张图必须再次通过逻辑接口，插件不能绕过终检。

领域层仍然负责不能泛化的判断：

- 财务插件：跨页表格、精确十进制计算、现金流闭合和因果表述边界；
- PGKD 插件：正文、流程图、算法三种载体对齐，字面索引保留和未消解歧义保留。

## 实验结果

- 财务生长重放结果与冻结的 `GDU_LOGIC_REAL_SLICE_V0_2.json` 对象级完全相同；
- PGKD 生长重放结果与冻结的 `GDU_LOGIC_METHOD_SLICE_V0_2.json` 对象级完全相同；
- 新增框架测试覆盖来源定位缺失、ID 冲突、生长追溯缺失、插件篡改输入、插件产生非法逻辑图和确定性重放；
- 全仓回归为 `209 passed, 5 skipped`。

## 对研究的意义

这一步证明的不是“GDU 已经适用所有领域”，而是两类性质不同的生长任务可以共用一个不改变原结果的安全事务层。因此，后续更换文档时，不需要重写“如何安全生长”，只需要研究“该领域的候选依据什么规则才能通过”。

这也明确了一个边界：目前仍需要人工编写领域验证和节点构建规则。下一步不应继续增加框架功能，而应测量第三个任务接入时需要编写多少领域代码，以判断当前抽象是否真正降低了迁移成本。
