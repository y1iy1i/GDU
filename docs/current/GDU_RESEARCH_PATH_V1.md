# GDU V1 研究路径

> 版本：V1  
> 日期：2026-08-21  
> 定位：当前研究主线与实现约束

## 1. 研究对象

GDU（Generative Document Understanding，生成式文档理解单元）研究如何把长文档转换为一张可查询、可推理、可追溯、可修订且能继续生长的外部知识图。

GDU 不以固定长度 Chunk 作为最终知识单元。Chunk 可以用于 Builder 分段读取原文，但正式回答来自经过逻辑检查的命题、推理、冲突和证据路径。

这里的“推理路径”是用户可以检查的外显理由链，不保存、不要求模型披露内部思维过程。

## 2. 当前核心问题

当前研究已经从“这种图能否推理和生长”转向“Builder 能否稳定地把新文档编译成这种图”。

核心研究问题是：

> 能否使用统一的 Builder，在少量人工参与下，从不同类型文档中构建出来源完整、范围清晰、关系可计算、错误可撤销的 GDU，并通过多轮主动成长与问答期成长逐步提高覆盖？

## 3. GDU 的固定逻辑架构

V1 采用“三层逻辑主干＋两个横向模块”。它定义 Builder 的目标输出，也定义问答执行时的计算规则。

```text
                    TMS / PROV
             依赖、来源、版本、失效传播
                         │
                         ▼
AIF式表示 → ASPIC+式论证构造 → Dung式接受计算
    │
    └──────── Belnap四值信息状态
```

### 3.1 表示层：AIF-like

保存：

- `Evidence`：原文证据及物理位置；
- `Claim`：可讨论真假、正反或适用性的命题；
- `Inference`：一次前提到结论的规则应用；
- `Conflict`：对结论、前提或规则适用性的攻击；
- `Context`：文档、章节、对象、时间、口径和场景。

### 3.2 论证层：ASPIC+-like

将表示层编译为结构化论证，区分：

- `strict`：精确计算、定义展开、确定阈值检查等严格推理；
- `defeasible`：可被更强证据、例外或冲突推翻的推定；
- `rebut`：攻击结论；
- `undermine`：攻击前提；
- `undercut`：攻击可废止规则的适用性。

### 3.3 接受层：Dung grounded semantics

对论证和攻击关系计算：

- `accepted`：当前可用于正式回答；
- `rejected`：当前不能进入正式回答；
- `undecided`：现有信息不足以决定。

### 3.4 横向模块：Belnap

记录命题收到的正反信息：

- `NEITHER`：正反信息都不足；
- `TRUE_ONLY`：只有正面信息；
- `FALSE_ONLY`：只有反面信息；
- `BOTH`：正反信息同时存在。

Belnap 保留信息冲突，不替代论证接受计算。

### 3.5 横向模块：TMS / PROV

- TMS 维护前提、推理和结论的依赖，支持节点失效后的局部重算；
- PROV 保存源文件哈希、页码、表格或算法位置、生长事件和版本历史。

## 4. Builder 与 GDU 的关系

GDU 是目标知识结构，Builder 是将原文编译成该结构的程序。

```text
原文档 = 源材料
Builder = 编译器
三层＋两模块 = 目标逻辑接口
GDU图 = 可执行、可追溯的编译产物
```

Builder 不另外定义一套知识架构。它的每个输出都必须进入三层主干或两个横向模块中的明确位置。

## 5. Builder V1 最小架构

### 5.1 Evidence Reader

将 PDF 或其他文档转换为带物理位置的证据块：

```text
block_id
physical_page
block_type
text
source_locator
source_hash
```

分段是读取手段，不是最终知识表示。

### 5.2 Representation Compiler

将证据块转换为：

- Evidence；
- 原子化 Claim；
- Claim 类型与极性；
- Context；
- Provenance。

首版只覆盖事实、定义、规则、结论、限制与冲突六类语义角色。

### 5.3 Argument Compiler

将 Claim 组织为：

- 联合前提；
- 严格或可废止推理；
- 结论；
- rebut、undermine 或 undercut；
- 条件、例外和规范力。

### 5.4 Semantics Executor

复用已有确定性逻辑引擎，计算论证接受状态、Belnap 信息状态和受影响子图。

### 5.5 Validator and Promotion

所有新内容先进入隔离候选区，通过来源、Context、数值、语义和逻辑接口检查后，以新版本形式晋升到正式 GDU。

### 5.6 Growth Controller

管理建库期成长与问答期成长：

```text
探测问题
→ 执行图查询
→ 识别断链或缺失 Atom
→ 从相邻节点有边界扩散
→ 必要时回查原文
→ 生成隔离候选
→ 验证与晋升
→ 重新计算三层＋两模块
```

## 6. Builder 的构建顺序

### 第一步：统一证据块接口

先稳定页码、段落、表格、图像、来源定位和哈希的输入形式。可接入 MinerU、PageIndex 或其他解析器，但 Builder 内部只使用统一接口。

### 第二步：构建最小文档地图

提取章节、主要实体、核心定义、显式结论、表格和图像位置。文档地图用于调度后续读取，不直接充当正式推理图。

### 第三步：构建表示层种子图

只写入来源明确的核心 Evidence、Claim、Context 和 Provenance。种子图不追求完整，但必须可追溯。

### 第四步：构建论证层

根据原文和命题内容提出前提、结论、规则强度、限制和冲突候选，通过接口检查后写入新版本。

### 第五步：运行建库期成长

采用“最少轮数＋最大轮数＋收敛判断”：

- 第1轮：主题、定义、实体和主要结论；
- 第2轮：因果、组成、条件和推导关系；
- 第3轮：限制、例外、冲突、不确定性和其他解释；
- 后续轮：针对图中的薄弱区域、断链和高频回查位置扩散。

连续两轮的有效新增和问题覆盖改善都很少时，建库期成长结束。

### 第六步：盲测与交付

使用未参与建图的问题检验可回答率、证据覆盖、推理路径完整度、误答阻断和原文回查率。

### 第七步：问答期继续成长

正式 GDU 不是静态产物。用户问题可继续触发缺口检测、原文回查、候选验证、版本晋升和局部重算。

## 7. V1 近期实验路径

### 实验 1：证据块接口

目标：将现有三份文档统一转换为带页码、类型、位置和哈希的 Evidence Block，并保持现有证据定位结果。

通过条件：

- 原文块可稳定重放；
- 物理页和表格、图、算法位置不丢失；
- 文档解析器可替换，内部接口不变。

实现与三文档验证见 [Builder V1 证据接口报告](../experiments/builder/GDU_BUILDER_V1_EVIDENCE_INTERFACE_REPORT.md)。当前已完成按页文本和类型化元素的统一入口；表格、图和算法区域的真实坐标仍取决于后续版面解析器。

### 实验 2：Representation Compiler

目标：自动提出 Evidence、原子 Claim、语义角色、极性和 Context，通过来源包络验证后进入种子图。

通过条件：

- 数字、单位、符号和规范力不被改写；
- 一个 Claim 只表达一个主要可检查内容；
- 实体、时间、口径和场景不被默认合并；
- 每个来源 Claim 可回到 Evidence Block。

候选契约、理论筛选和确定性编译实现见 [Builder V1 表示层编译器报告](../experiments/builder/GDU_BUILDER_V1_REPRESENTATION_COMPILER_REPORT.md)。当前已证明候选可安全进入种子图；模型自动抽取的准确率和召回率将通过下一次盲测量化。

### 实验 3：Argument Compiler

目标：自动提出联合前提、结论、严格/可废止类型与攻击位置，由确定性逻辑接口执行终检。

通过条件：

- 不把共现关系写成因果或支持；
- 不把局部合格写成整体合格；
- 不把来源冲突静默改成单一结论；
- 推理和冲突通过当前三层逻辑接口。

### 实验 4：建库期成长控制

目标：比较0、1、3、5、8轮成长后的知识覆盖、错误和成本，建立文档复杂度与成长轮数的实验关系。

观察指标：

- 每轮新增有效 Claim 和 Inference；
- 每轮重复、错误和被拒绝候选；
- 盲测可回答率与证据覆盖；
- 问答期原文回查率；
- 模型调用、时间和费用；
- 连续轮次的边际收益。

### 实验 5：Builder 对照

目标：用统一 Builder 重建财务、论文方法和规范标准三个案例，与当前人工构建图比较。

核心指标：

- Claim 精确率和召回率；
- Inference 与 Conflict 准确率；
- Evidence 锚定准确率；
- Context 完整率；
- 高影响错误率；
- 人工领域代码减少量；
- 最终问答和失效重算是否保持现有结果。

## 8. 成长轮数研究方法

不使用单一固定轮数适配所有文档。V1 采用：

```text
最少成长轮数
+ 最大成长轮数
+ 收敛条件
+ 成本上限
```

文档复杂度不只用页数衡量，还包括：

- 章节数量与层级；
- 主要实体数量；
- 表格、图和算法密度；
- 跨页与跨章引用；
- 条件、例外和规范条款密度；
- 冲突和备选解释数量；
- 多步推理路径长度。

建库期不追求完美覆盖。它要交付一张可用、可发现自身缺口、可继续回查和生长的图。

## 9. 已有实验证据

### 9.1 三层＋两模块

已在真实年报切片上完成精确财务闭合、错误经验推断阻断和局部失效重算。

### 9.2 可审计回答

答案只使用 `accepted` 论证，并返回证明步骤、原文证据、限制命题和被拒绝结论。

### 9.3 查询规划与缺口检测

已验证同义问法、错误前提、Context 错配、目标 Atom 缺失和最多两跳有类型扩散。

### 9.4 三次正式生长

1. 财务领域：跨页表格和精确数字闭合；
2. 论文方法：正文、流程图与算法索引冲突；
3. 规范文档：义务、局部满足、违规和整体合规判断。

三个领域共用同一通用晋升事务层。当前全仓回归为 `236 passed, 5 skipped`。

## 10. 当前边界

已有结果支持 GDU 是一个值得继续研究的原型，但不支持以下更强结论：

- 还没有证明 GDU 在多领域稳定优于强 Chunk RAG 或其他知识图方案；
- 还没有证明 Builder 能在少量人工参与下构建同等质量的图；
- 还没有建立文档复杂度与成长轮数的经验关系；
- 还没有证明当前两跳扩散适用于大规模图；
- 当前领域插件仍包含较多手工命题、规则和验证代码。

## 11. V1 的实现范围

V1 集中实现：

- 页面级 Evidence Block 接口；
- 最小文档地图；
- Representation Compiler；
- Argument Compiler；
- 现有逻辑、回答、晋升和重算引擎接入；
- 建库期成长控制；
- 三领域回放、盲测与成本对照。

V1 不将以下内容作为首批实现：

- 自研 OCR 和完整 PDF 版面引擎；
- 大规模分布式图存储；
- 数十种自定义节点和关系；
- 完整 LegalRuleML 兼容；
- 多模型投票与自动参数搜索；
- 无边界的全图扩散。

## 12. V1 完成判据

V1 以实验结果而不是文件数量作为判据：

1. 统一 Builder 能对三个现有领域产生符合三层＋两模块的图；
2. 现有财务、来源冲突和规范合规问题的核心结论与证据保持；
3. Builder 不读取 Gold，评价问题不参与建图；
4. 高影响错误能在晋升前被拒绝或在回答前被阻断；
5. 每个正式结论可追溯到原文和生长版本；
6. 失效后的局部重算与全量重算一致；
7. 领域专用节点构建代码相对第三次实验出现明显减少；
8. 成长轮次、边际收益、成本和盲测覆盖形成可重放记录。

## 13. 紧接的实现起点

V1 实现从 Evidence Block 接口开始，先用当前三份已核对文档保证输入稳定，再构建 Representation Compiler。

第一个量化目标是：

> 在不修改现有逻辑、回答和晋升事务的前提下，自动生成第三次规范文档实验的 Evidence 和原子 Claim，显著减少手写领域代码，并保持条款、数值、规范力和原文位置不变。
