# GDU Builder V1 证据接口与最小文档地图报告

## 1. 实验意义

本次工作是 Builder V1 的第一个可运行部分。它先解决一个基础问题：无论上游使用 PDF 文本层、MinerU、PageIndex 或其他解析器，进入 GDU 构建流程的原文都必须有统一、可验证、可重放的表示。

这一层还不会自动生成 Claim 或推理关系。它的价值是为后续编译提供不会丢失来源的原料。

## 2. 已实现内容

### 2.1 Evidence Block

每个证据块固定记录：

- 文档标识与源文件 SHA-256；
- PDF 物理页码与页内顺序；
- 块类型，包括标题、段落、表格、图、算法和脚注；
- 原文、位置定位符和可选坐标；
- 解析器身份、内容哈希和确定性 Block ID。

系统只合并布局产生的多余空白，不改写数字、单位、正负号或标点。

### 2.2 确定性验证

进入 Builder 之前会检查：

- 页码是否超出源 PDF 范围；
- Block ID、定位符和页内序号是否冲突；
- 原文或位置改变后，哈希是否仍然匹配；
- 证据块是否属于当前文档和当前解析器；
- 是否存在空文本、非法坐标或非物理顺序。

因此，后续 Claim 不需要信任模型自己声明的页码，只能引用已验证的 Evidence Block。

### 2.3 上游解析器适配

当前有两种输入方式：

1. 将现有 v0 PDF 按页读取结果转换成 `page_text` 证据块；
2. 接收已经区分标题、段落、表格、图和算法的类型化元素。

第一种用于立即运行和兼容旧输入；第二种是后续接入 MinerU 等版面解析器的正式接口。

### 2.4 最小文档地图

已实现一个保守的 Document Map：

- 如果上游提供了明确的标题块，按标题组织章节；
- 如果只有整页文本，仅生成一个页级文档区域；
- 不从普通文本的外观猜测标题，避免把错误结构带入后续推理。

Document Map 只负责调度读取，不是正式知识图。

## 3. 真实文档验证

用三个现有研究输入的原 PDF 进行了验证，并锁定了已知源文件哈希。测试只读取原实验涉及的物理页，没有将原文全文写入仓库。

| 文档类型 | PDF 总页数 | 验证物理页 | 生成证据块 | 结果 |
|---|---:|---|---:|---|
| 财务年报 | 189 | 15、72–73、156–157 | 5 | 来源哈希、页码、块哈希与地图通过 |
| PGKD 论文 | 13 | 3–4 | 2 | 来源哈希、页码、块哈希与地图通过 |
| GB 45438-2025 | 19 | 5、7–8、17 | 4 | 来源哈希、页码、块哈希与地图通过 |

三份文档通过当前 PDF 文本层适配器进入时，Document Map 都保持 `page_only`。这是有意的保守结果：现有按页读取器没有提供可靠的元素类型，Builder 不伪造章节结构。

## 4. 自动测试

新增测试覆盖：

- 相同输入的 ID 和哈希稳定性；
- 物理页顺序与页内序号；
- 空块、超界页码和重复定位符拒绝；
- 原文篡改和解析器不一致检测；
- v0 证据包迁移与非权威导航文本隔离；
- 页级地图和标题级地图。

## 5. 当前边界与下一实验

证据接口已经稳定，但不等于 Builder 已经建成。当前按页文本适配器无法保留表格单元格、图区域和精确段落坐标；这些能力需要类型化版面解析器提供。

下一实验是 Representation Compiler：从 Evidence Block 中生成原子 Claim、Context 和 Provenance 候选，再用确定性规则阻止数值改写、范围合并和无来源命题。

## 6. 重放入口

```bash
PYTHONPATH=src python scripts/build_evidence_manifest_v1.py \
  --source-pdf /path/to/paper.pdf \
  --document-id example-document \
  --pages 1-3,7 \
  --expected-source-sha256 <sha256> \
  --output /tmp/evidence.json \
  --map-output /tmp/document-map.json
```

输出 JSON 不包含当前时间，因此相同文档、解析器和页面范围可产生相同哈希。
