## 3. 四个比较控制项审计

### 3.1 集合最值

模型正确生成：

```text
comparison_kind = extremum
operator = min
metric = 运行成本
reference_set = 全部候选方案
```

候选仅因没有重复提交 `SemanticCue(comparison)` 被拒绝。`ComparisonConstraint.surface=运行成本最低` 已经逐字追溯，额外cue没有提供新信息，属于校验器误伤。

### 3.2 固定阈值

模型正确生成 `threshold + lte + 10 MB`，Quantity和规范力也正确。同样仅因没有重复comparison cue被拒绝，属于同一问题族的校验器误伤。

### 3.3 对象间比较

模型正确识别 `relative + lt`，但把 `reference_metric` 写成“响应时间”，Gold要求“方案乙的响应时间”。这不是简单措辞差异：当前结构没有独立的 `subject/reference_subject`，迫使Gold把参考对象塞进metric。下一版应补充比较双方对象，而不是把本例加入字符串特例。

### 3.4 来源明确的未判定状态

模型正确写出 `epistemic_status=undetermined` 和原文cue“尚未判定”，但又把 `polarity` 写成不存在的 `undetermined`。这说明模型仍会混淆命题形式与认识状态；本地校验正确阻止了候选进入正式图。

## 4. 去除通用冗余后的离线重放

原始响应和原始评分保持不变。删除“Constraint已经有可追溯surface仍必须重复提交comparison cue”的通用规则后，对同一响应离线重放：

|---|---:|
| 严格结构匹配 | 11/13（84.62%） |
| 校验通过 | 12/13（92.31%） |
| 剩余问题 | comparison_scope 1；polarity_scope 1 |

该提升没有新增模型调用，也没有修改模型输出或Gold。

## 6. 当前判断

Builder V1.1已经能够稳定处理本轮的表格证据、数值规范化、算法字面命题和规范条款。比较类型的主干方向得到支持：模型成功区分了threshold、relative和extremum。

它仍未完成，剩余两个明确问题是：

1. 相对比较必须显式绑定左右对象；
2. `undetermined`等认识状态需要进一步防止模型误写入命题polarity。

下一步应只解决这两个结构问题，再做一个小型未见变形测试，不需要重新扩大整个Schema。
